# 決済インボックス機能仕様書

- 文書状態: Draft（PR #28 実装対応版）
- 対象アプリ: 通知箱 Android
- 対象機能: 決済インボックス（ベータ）
- 対象バージョン: v0.1.x 技術ベータ
- 最終更新日: 2026-07-26
- 関連設計書: [`payment-inbox-design-ja.md`](payment-inbox-design-ja.md)

## 1. 目的

Androidの通知アクセスを既に利用している「通知箱」に、決済通知から金額・店舗・取引種別を端末内で抽出し、簡易的に確認できる「決済インボックス」を統合する。

本機能は総合家計簿、銀行口座連携、会計ソフト、決済明細の正規データソースを目指さない。通知に含まれる情報だけを対象とし、入力負担を減らす補助的な記録・確認機能として提供する。

## 2. 背景と解決する課題

決済アプリやカードアプリを複数利用すると、支払履歴の確認先が分散する。一方、別の家計簿アプリへ通知アクセスを追加で許可することには、権限・プライバシー・運用負担が伴う。

通知箱は既に以下を備えている。

- `NotificationListenerService`による通知取得
- 通知タイトル・本文の安全な抽出
- bounded単一キューによる取込順序の保証
- Roomによる端末内保存
- `INTERNET`権限を持たないプライバシー境界
- 通知本文をログや診断状態へ残さない運用

そのため、決済解析を別アプリとして新設せず、通知箱の派生機能として統合する。

## 3. ゴール

### 3.1 ユーザーゴール

- PayPayの対象通知を受信した後、金額・店舗・取引種別を一画面で確認できる。
- 今月の推定支出を確認できる。
- 通知本文をクラウドや外部AIへ送らずに利用できる。
- 不要になった決済履歴をアプリ内から削除できる。

### 3.2 プロダクトゴール

- 既存の通知アクセスと通知取込基盤を再利用する。
- 通常の通知履歴機能の信頼性を低下させない。
- 決済通知の書式変更や対応アプリ追加に追従できる構造にする。
- 誤解析を完全自動確定せず、ベータ機能であることを明示する。

### 3.3 完了条件

次をすべて満たした状態を、本MVPの完了とする。

1. PayPayパッケージの対象通知だけが決済解析対象になる。
2. 金額を抽出できない通知は決済イベントとして保存されない。
3. キャンペーン等の販促通知は、金額を含んでいても保存されない。
4. 解析した決済情報が通常の通知履歴とは別のRoomテーブルへ保存される。
5. 同一通知キーの再同期で決済イベントが重複しない。
6. 決済解析または保存に失敗しても、通常の通知履歴保存が成功した状態を維持する。
7. 決済タブで今月の集計、履歴、保存失敗状態を確認できる。
8. 決済履歴を確認ダイアログ経由で全消去できる。
9. v1、v2、v3からDB version 4へ移行できる。
10. 単体テスト、lint、debug build、Room migration検証、インストール済みAPK migration検証が成功する。

## 4. 対象ユーザー

- Android端末でPayPayを利用しているユーザー
- 通知箱へ通知アクセスを許可しているユーザー
- 総合家計簿より、簡易的かつ端末内完結の確認を求めるユーザー
- 銀行・カードの認証情報やクラウド同期を使いたくないユーザー

## 5. ユースケース

### UC-01 支払い通知を記録する

1. PayPayが支払い完了通知を投稿する。
2. 通知箱が通常の通知履歴として保存する。
3. 決済解析器が通知タイトル・本文から金額、店舗、取引種別を抽出する。
4. 抽出結果を決済イベントとして端末内へ保存する。
5. ユーザーが決済タブで確認する。

### UC-02 返金通知を集計へ反映する

1. PayPayが返金または取消通知を投稿する。
2. 決済解析器が取引種別を返金として判定する。
3. 今月の推定支出を「支払い合計 - 返金合計」で表示する。

### UC-03 再接続同期時の重複を防ぐ

1. 通知リスナーが再接続する。
2. 同じOS通知がスナップショット同期へ再登場する。
3. 元通知キーを主キーとしてupsertし、決済イベントを重複作成しない。

### UC-04 解析できない通知を無視する

1. PayPayからキャンペーン、クーポン、残高案内などが届く。
2. 決済として確定できない場合は保存しない。
3. 通常の通知履歴には従来どおり保存する。

### UC-05 決済履歴を削除する

1. ユーザーが決済タブで「決済履歴をすべて削除」を選択する。
2. 確認ダイアログを表示する。
3. 承認後、決済イベントだけを全削除する。
4. 通常の通知履歴と元のOS通知は変更しない。

## 6. スコープ

### 6.1 MVPに含む

- PayPay Androidアプリの通知解析
- 日本円金額の抽出
- 店舗名の抽出（通知に明示される場合のみ）
- 取引種別の分類
  - 支払い
  - 返金・取消
  - チャージ
  - 送金
  - 受取
  - 要確認
- 今月の支払い合計、返金合計、推定支出
- 最大500件の決済履歴表示
- 解析信頼度と解析器バージョンの保存
- 決済保存成功・失敗の内容非保持カウンター
- 決済履歴の確認付き全消去
- Room DB version 4 migration
- 端末内処理、外部送信なし

### 6.2 MVPに含まない

- 銀行口座、クレジットカード、電子マネーの公式API連携
- SMS解析
- メール解析
- レシートOCR
- カテゴリ自動分類
- 予算管理
- クラウド同期、家族共有、複数端末同期
- CSV・会計ソフトへのエクスポート
- 通知に存在しない店舗、商品、税区分、決済手段の推測
- 通貨換算、外貨決済
- 自動削除、重複候補の推測統合
- 個別イベントの編集、削除、確定操作
- iOS対応
- 広告、サブスクリプション、課金

## 7. 機能要件

### 7.1 対象通知判定

| ID | 要件 |
|---|---|
| PAY-FR-001 | 決済解析対象は、登録済み解析器が対応すると宣言したパッケージ名に限定する。 |
| PAY-FR-002 | 初期版はPayPayのパッケージ `jp.ne.paypay.android.app` のみ対応する。 |
| PAY-FR-003 | 対応外パッケージの通知は、金額や決済文言を含んでいても決済イベントへ保存しない。 |
| PAY-FR-004 | 通知内容が空、またはAndroid・通知元アプリにより取得不能の場合は決済イベントへ保存しない。 |

### 7.2 正規化と金額抽出

| ID | 要件 |
|---|---|
| PAY-FR-010 | タイトルと本文を結合し、Unicode NFKC正規化を行ってから解析する。 |
| PAY-FR-011 | `1,280円`、`1280 円`、`¥1,280`、`￥1,280`形式を解析できる。 |
| PAY-FR-012 | 全角数字・全角カンマをNFKC正規化後に解析できる。 |
| PAY-FR-013 | 抽出金額は整数の日本円として保存する。小数、外貨、換算は対象外とする。 |
| PAY-FR-014 | 金額を抽出できない通知は保存しない。 |

### 7.3 誤検出抑制

| ID | 要件 |
|---|---|
| PAY-FR-020 | キャンペーン、クーポン、ポイント還元、抽選、当選訴求を含む通知は保存しない。 |
| PAY-FR-021 | 金額が含まれていても、取引種別または汎用取引完了文言を検出できない通知は保存しない。 |
| PAY-FR-022 | 単なる残高表示や販促上の金額を決済として記録しない。 |
| PAY-FR-023 | 誤検出抑制を、対応アプリごとの解析器単体テストで固定する。 |

### 7.4 取引種別

取引種別の判定は次の優先順とする。複数の語が同一通知に含まれる場合、上位を採用する。

1. 返金・取消
2. チャージ
3. 受取
4. 送金
5. 支払い
6. 要確認

| ID | 要件 |
|---|---|
| PAY-FR-030 | `返金`、`払い戻し`、`取消`、`キャンセル`を返金として扱う。 |
| PAY-FR-031 | `チャージ`、`残高に入金`をチャージとして扱う。 |
| PAY-FR-032 | `受け取り`、`受取`、`受領`を受取として扱う。 |
| PAY-FR-033 | `送金`、`送付`を送金として扱う。 |
| PAY-FR-034 | `支払い`、`お支払い`、`決済`を支払いとして扱う。 |
| PAY-FR-035 | 汎用取引完了文言を検出したが種別を確定できない場合は、要確認として保存できる。 |

### 7.5 店舗名

| ID | 要件 |
|---|---|
| PAY-FR-040 | `利用先`、`支払先`、`店舗`、`お店`ラベルの後続文字列から店舗名を抽出できる。 |
| PAY-FR-041 | `○○でのお支払い`等の文面から店舗名を抽出できる。 |
| PAY-FR-042 | 店舗名が通知に含まれない場合は、`null`として保存し、UIでは「店舗不明」と表示する。 |
| PAY-FR-043 | 店舗名は先頭行のみを採用し、1文字以上80文字以下に制限する。 |
| PAY-FR-044 | 店舗名を外部データベースやAIで補完しない。 |

### 7.6 保存

| ID | 要件 |
|---|---|
| PAY-FR-050 | 決済イベントは通常の通知履歴とは別の`payment_events`テーブルへ保存する。 |
| PAY-FR-051 | 通知タイトルと本文を`payment_events`へ複製しない。 |
| PAY-FR-052 | 元通知の一意キーを決済イベントの主キーとして使用する。 |
| PAY-FR-053 | 再同期または同一キーの再取込時はupsertし、重複行を作成しない。 |
| PAY-FR-054 | 解析器ID、解析器バージョン、信頼度を保存する。 |
| PAY-FR-055 | 決済イベントはユーザーが全消去するか、アプリをアンインストールするまで保持する。 |
| PAY-FR-056 | 画面表示は新しい順に最大500件とする。集計は表示上限とは独立して対象期間の全件を使用する。 |

### 7.7 集計

| ID | 要件 |
|---|---|
| PAY-FR-060 | 端末のローカルタイムゾーンにおける当月1日0時を集計開始時刻とする。 |
| PAY-FR-061 | 支払い合計は`PURCHASE`イベントの金額合計とする。 |
| PAY-FR-062 | 返金合計は`REFUND`イベントの金額合計とする。 |
| PAY-FR-063 | 推定支出は`支払い合計 - 返金合計`とする。 |
| PAY-FR-064 | チャージ、送金、受取、要確認は推定支出へ加算しない。 |
| PAY-FR-065 | 要確認件数を表示する。 |
| PAY-FR-066 | 画面上で「推定」であることと、通知だけを根拠にしていることを明示する。 |

### 7.8 UI

| ID | 要件 |
|---|---|
| PAY-FR-070 | ホーム下部ナビゲーションへ「決済」タブを追加する。 |
| PAY-FR-071 | 決済タブにベータ表記とPayPayのみ対応する説明を表示する。 |
| PAY-FR-072 | 今月の推定支出、解析済み件数、要確認件数を表示する。 |
| PAY-FR-073 | 各イベントへ店舗名、金額、アプリ名、取引種別、日時を表示する。 |
| PAY-FR-074 | 取引種別が要確認の場合は注意表示を行う。 |
| PAY-FR-075 | 決済データがない場合は空状態を表示する。 |
| PAY-FR-076 | DB読取失敗時はエラー状態を表示し、通常の通知履歴保存は継続する旨を示す。 |
| PAY-FR-077 | 決済保存失敗がある場合、通知内容を含まない件数ベースの警告を表示する。 |
| PAY-FR-078 | 決済履歴の全消去前に確認ダイアログを表示する。 |
| PAY-FR-079 | 全消去失敗時はユーザーへ再試行可能なエラーを表示する。 |

### 7.9 失敗境界

| ID | 要件 |
|---|---|
| PAY-FR-080 | 通常の通知履歴保存を先に完了し、その後に決済派生処理を実行する。 |
| PAY-FR-081 | 決済解析・保存例外によって通常の通知取込コマンドを失敗扱いにしない。 |
| PAY-FR-082 | Coroutineキャンセルは握りつぶさず再送出する。 |
| PAY-FR-083 | 決済保存失敗は通知本文・店舗名・金額・通知キーを含まないカウンターだけへ記録する。 |
| PAY-FR-084 | 未対応通知、解析対象外通知、金額なし通知はエラーではなく正常な非対象として扱う。 |

### 7.10 削除

| ID | 要件 |
|---|---|
| PAY-FR-090 | ユーザーは決済イベントを一括削除できる。 |
| PAY-FR-091 | 決済イベントの削除は、通常の通知履歴、分類ルール、統計、元のOS通知へ影響させない。 |
| PAY-FR-092 | アプリのアンインストールによりAndroidの通常動作で決済イベントが削除される。 |

## 8. 非機能要件

### 8.1 プライバシー

| ID | 要件 |
|---|---|
| PAY-NFR-001 | 解析・保存・集計を端末内で完結する。 |
| PAY-NFR-002 | `INTERNET`権限、外部API、外部AI、広告SDK、解析SDK、クラッシュ収集SDKを追加しない。 |
| PAY-NFR-003 | Androidバックアップおよび端末間データ転送を有効化しない。 |
| PAY-NFR-004 | 決済データを他アプリへ共有・送信する機能をMVPへ追加しない。 |
| PAY-NFR-005 | プライバシーポリシーとGoogle Play Data safety作業票を実装と一致させる。 |

### 8.2 セキュリティ

| ID | 要件 |
|---|---|
| PAY-NFR-010 | 決済画面を含むアプリ画面は既存の`FLAG_SECURE`境界を維持する。 |
| PAY-NFR-011 | 通知本文、抽出金額、店舗名をログへ出力しない。 |
| PAY-NFR-012 | SQLはRoom DAOと定義済みmigrationを通して実行する。 |

### 8.3 信頼性

| ID | 要件 |
|---|---|
| PAY-NFR-020 | 再接続同期で同一通知が複数回入力されても、DB上の決済イベントは1件である。 |
| PAY-NFR-021 | 決済機能の障害が通知履歴・分類・サマリー機能へ波及しない。 |
| PAY-NFR-022 | DB migrationは破壊的migrationを使用しない。 |
| PAY-NFR-023 | 既存通知、ピン留め、手動分類、アプリ別ルール、分類統計をmigration後も保持する。 |

### 8.4 性能

| ID | 要件 |
|---|---|
| PAY-NFR-030 | 解析は同期的な文字列処理とし、ネットワーク待機を発生させない。 |
| PAY-NFR-031 | 画面の履歴読取は最大500件に制限する。 |
| PAY-NFR-032 | 月次集計はRoomの集約SQLで実行し、全行をUI層へロードして計算しない。 |

### 8.5 保守性

| ID | 要件 |
|---|---|
| PAY-NFR-040 | 対応アプリごとに`PaymentNotificationParser`実装を分離する。 |
| PAY-NFR-041 | 解析器はAndroid APIへ依存しないPure Kotlinとして単体テスト可能にする。 |
| PAY-NFR-042 | 解析仕様変更時は`parserVersion`を更新する。 |
| PAY-NFR-043 | 新規対応アプリ追加時に既存パーサーを変更せず、Registryへ追加できる。 |

## 9. データ項目

| 項目 | 型 | 必須 | 説明 |
|---|---|---:|---|
| `sourceNotificationKey` | String | 必須 | 元通知の一意キー。主キー。 |
| `packageName` | String | 必須 | 通知元アプリのパッケージ名。 |
| `appLabel` | String | 必須 | 通知元アプリの表示名。 |
| `amountYen` | Long | 必須 | 抽出した整数の日本円金額。 |
| `merchantName` | String? | 任意 | 通知から抽出できた店舗名。 |
| `transactionType` | String | 必須 | `PURCHASE`、`REFUND`、`CHARGE`、`TRANSFER_OUT`、`TRANSFER_IN`、`UNKNOWN`。 |
| `occurredAtMillis` | Long | 必須 | 元通知の投稿時刻。Unix epoch milliseconds。 |
| `parserId` | String | 必須 | 解析器識別子。初期版は`paypay`。 |
| `parserVersion` | Int | 必須 | 解析ルールのバージョン。 |
| `confidencePercent` | Int | 必須 | 解析信頼度。0〜100。 |
| `status` | String | 必須 | 初期値`UNREVIEWED`。将来の確認状態拡張用。 |

通知タイトルと本文はこのテーブルへ保存しない。

## 10. 画面仕様

### 10.1 ナビゲーション

下部ナビゲーションは次の3タブとする。

1. 通知
2. 決済
3. サマリー

### 10.2 決済画面

上から次の順で表示する。

1. 画面タイトル「決済インボックス（ベータ）」
2. 対応範囲と通知情報のみを使用する旨の注記
3. 今月の推定支出カード
4. 解析済み件数・要確認件数
5. 決済保存失敗警告（失敗がある場合のみ）
6. 決済イベント一覧、または空状態
7. 端末内保存と通知本文非複製の注記
8. 決済履歴全消去アクション

### 10.3 金額表示

- 日本ロケールの円表記を使用する。
- 小数桁は表示しない。
- 推定支出が負値となる場合も、そのまま返金超過として表示する。

## 11. DB migration要件

- Room DB versionを3から4へ更新する。
- `payment_events`テーブルを追加する。
- `occurredAtMillis`、`packageName`、`transactionType`へ非一意indexを追加する。
- version 1から4、version 2から4、version 3から4のmigration経路を成立させる。
- 既存データを変換または削除しない。
- v1 APKで作成した実DBを現行APKへ上書き更新するCI検証を通過させる。
- Roomが生成するschema 4 JSONをリポジトリへコミットする。

## 12. 受入基準

### 12.1 解析

- [ ] `利用先：セブン-イレブン\n1,280円のお支払いが完了しました`から、1,280円・セブン-イレブン・支払いを抽出できる。
- [ ] 全角数字の`５，０００円`を5,000円として解析できる。
- [ ] 支払い文言を含む返金通知を返金として優先判定できる。
- [ ] 金額のない通知を保存しない。
- [ ] 金額を含むキャンペーン通知を保存しない。
- [ ] 単なる残高通知を保存しない。
- [ ] 対応外パッケージを保存しない。

### 12.2 保存と障害

- [ ] 同一通知キーを2回入力しても1行である。
- [ ] 決済保存失敗時も通常の通知履歴が保存される。
- [ ] 決済保存失敗カウンターへ通知内容が含まれない。
- [ ] 決済全消去が通常の通知履歴へ影響しない。

### 12.3 UI

- [ ] 決済タブを表示できる。
- [ ] 月次推定支出を表示できる。
- [ ] 直近最大500件を新しい順に表示できる。
- [ ] 空状態、読取エラー、保存失敗、削除失敗を区別して表示できる。
- [ ] 全消去前に確認ダイアログを表示する。

### 12.4 migration・CI

- [ ] `lintDebug`成功
- [ ] `assembleDebug`成功
- [ ] Windows CI成功

## 13. 既知の制約

- PayPayの通知文面は外部アプリ側の変更により解析不能になる可能性がある。
- 通知設定、Android、端末メーカー、PayPay設定により通知本文が省略される場合がある。
- 通知が無効化されている取引は記録できない。
- 同一取引が複数の異なる通知キーで投稿された場合、MVPでは意味的な重複判定を行わない。
- 支払いとチャージ等が1件の通知に混在する場合、定義済み優先順位による単一種別だけを保存する。
- 「推定支出」は金融機関やPayPay公式明細と一致することを保証しない。
- 解析済みイベントの手修正機能はMVPに含まれない。

## 15. 変更管理

- 解析対象、保存項目、集計定義、保持期間、外部送信境界を変更する場合は、本仕様書を更新する。
- 解析キーワード・正規表現のみの変更でも、挙動が変わる場合は`parserVersion`と回帰テストを更新する。
- DB項目変更時はRoom version、migration、schema JSON、実APK migration検証を同一PRへ含める。
- プライバシー境界を変更する場合は、README、プライバシーポリシー、Google Play Data safety文書も同一PRで更新する。
